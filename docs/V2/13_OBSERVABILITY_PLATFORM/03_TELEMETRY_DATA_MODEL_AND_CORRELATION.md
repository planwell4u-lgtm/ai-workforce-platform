# 03_TELEMETRY_DATA_MODEL_AND_CORRELATION

**Version:** 1.1  
**Status:** Approved  
**Owner:** Observability Platform Owner  
**Phase:** Platform Architecture

---

# Purpose

This document defines the common telemetry envelope, correlation model, dimensions, cardinality controls, and lifecycle rules that let approved platform evidence be joined safely across requests, events, jobs, channels, integrations, and delivery environments. It does not define canonical domain schemas, customer profiles, conversation content, authorization facts, or business outcomes.

# Telemetry Envelope

Every telemetry record uses a versioned common envelope plus owner-defined safe attributes:

| Field | Purpose | Rule |
|---|---|---|
| `telemetry_id` | Immutable identity for the evidence record. | Generated by the producer or approved collector; never reused as domain identity. |
| `time_observed` | When the producing component observed the event. | Includes clock/source quality where relevant; does not replace canonical domain time. |
| `environment` | Delivery environment classification. | Never used as tenant or authorization proof. |
| `service` / `module` | Producing capability identity. | Stable registered name; owner-controlled. |
| `operation` | Bounded operation name. | Uses controlled vocabulary; excludes raw payloads/URLs containing protected values. |
| `outcome_category` | Safe classification such as accepted, failed, restricted, uncertain, or reconciled. | Defined/approved by the owning domain; never flattened into generic success. |
| `trace_id` / `span_id` | Distributed request/execution correlation. | Propagated through approved boundaries; access-controlled evidence only. |
| `correlation_id` | Cross-system/business-process reference. | Carries a non-sensitive reference; not a participant identity or authorization token. |
| `tenant_dimension` | Approved tenant-scoped analysis dimension. | Access-controlled and minimized; not permission evidence. |
| `version_reference` | Artifact/configuration/contract/agent/policy reference as applicable. | Safe identifier only; supports change correlation. |
| `error_class` / `retry_state` | Failure and recovery classification. | Sanitized controlled values; no raw exception secrets/payloads. |

Owner-defined attributes must declare purpose, classification, cardinality, access role, retention, and whether they are safe for metrics, logs, traces, dashboards, alerts, or export.

# Correlation Model

```text
Trusted request or channel input
        |
        +--> trace: bounded technical execution path
        +--> correlation: approved multi-step business/process relationship
        +--> domain reference: owner-controlled canonical record link
        |
        v
Safe telemetry envelopes across services, jobs, callbacks, and delivery attempts
```

Trace identifiers correlate technical work. Correlation identifiers link approved related work. Domain references point to owner-controlled records through protected access paths. These identifiers have different purposes and must not be overloaded to grant access, merge participants, imply tenant membership, or assert that separate outcomes are the same.

# Context Propagation Rules

- Inbound trusted requests start or continue an approved trace and carry only validated/safe context to downstream work.
- Asynchronous jobs, events, retries, callbacks, handoffs, and external-effect reconciliation preserve parent/correlation references when available and record a safe link when they are not.
- A receiving component validates propagated context against its own trusted identity, tenant, authorization, and input contracts. It does not trust a trace/correlation field as authorization.
- Context propagation is bounded by data classification and channel/security rules. Raw prompts, messages, transcript content, credentials, or participant identifiers are not inserted into correlation fields.
- When correlation is unavailable or contradictory, telemetry records the uncertainty rather than fabricating continuity.

# Dimensions and Cardinality

Approved standard dimensions include environment, service/module, operation, outcome category, version/configuration reference, dependency/provider category, retry/reconciliation state, safe region/capacity class, and tenant-scoped dimension where authorized. Domain owners may define additional dimensions only after evaluating investigation value, tenant/privacy impact, cardinality, cost, retention, dashboard/alert use, and migration compatibility.

High-cardinality or protected values—including raw tenant/customer/user identifiers, conversation/message identifiers, URLs, query strings, email addresses, phone numbers, prompts, document names, and provider payloads—are not routine metric labels. Where an approved investigation need exists, they are represented as access-controlled references or purpose-limited records rather than broadly queryable dimensions.

# Outcome and Error Taxonomy

Each domain registers its telemetry outcome categories and error classes. Shared categories may include `accepted`, `in_progress`, `succeeded`, `failed`, `restricted`, `cancelled`, `no_effect`, `degraded`, `uncertain`, and `reconciled`; their semantic meaning remains the domain owner's responsibility.

Telemetry must distinguish at least: request acceptance, internal processing, external provider acknowledgement, participant delivery, business-action completion, data recovery, and reconciliation. Observability does not collapse these into a single “success” number or resolve conflicts between owner assertions.

# Schema Evolution and Compatibility

Envelope and attribute changes are additive and versioned where possible. A removal, changed meaning, altered classification, cardinality increase, access change, or retention change requires owner review, consumer inventory, migration/rollback path, and updated dashboards/alerts/tests where affected.

Producers retain compatibility during the approved transition window. Consumers tolerate unknown additive fields and must not infer a new semantic from a field name alone. Telemetry schemas are not a backdoor public API or an excuse to expose domain internals.

# Access, Retention, and Data Handling

Telemetry fields are classified before collection. Observability enforces approved access, redaction, encryption, export, retention, deletion, residency, legal-hold, and audit mechanisms in cooperation with Security and Data. Domain owners remain responsible for identifying the minimum evidence necessary for their objective.

Derived metrics, dashboards, and alert payloads inherit the restrictions of their inputs. Aggregation does not automatically make data safe for cross-tenant, unrestricted, or external use. A telemetry export is subject to current identity, authorization, purpose, and lifecycle controls.

# Required Evidence

Before implementation approval, demonstrate envelope validation; correlation propagation across synchronous/asynchronous paths; trusted-context validation; cardinality controls; protected-field rejection/redaction; outcome-taxonomy registration; schema compatibility; tenant-safe query/access negatives; retention/export review; and representative trace-to-operations investigation evidence.
