# 31.2 Multi-Tenant Data Model

**Version:** 1.0\
**Phase:** 31 -- Database Architecture

# 1. Purpose

Defines the multi-tenant architecture for the AI Voice Agent SaaS
platform.

# 2. Objectives

-   Strong tenant isolation
-   Enterprise security
-   Horizontal scalability
-   Flexible subscription model
-   Feature isolation
-   Usage metering

# 3. Selected Strategy

**Shared Database + Shared Schema + Row Level Security**

Every business table contains:

``` text
tenant_id UUID NOT NULL
```

# 4. Tenant Hierarchy

``` text
Platform
├── Tenant
│   ├── Users
│   ├── Agents
│   ├── Calls
│   ├── Conversations
│   ├── Knowledge Bases
│   ├── Campaigns
│   └── Billing
```

# 5. Tenant Lifecycle

Created → Trial → Active → Suspended → Cancelled → Archived

# 6. Isolation Rules

-   Every API request resolves a tenant.
-   JWT contains tenant context.
-   PostgreSQL RLS filters all tenant-owned tables.
-   No cross-tenant joins.

# 7. Global vs Tenant Data

## Global

-   Countries
-   Languages
-   AI model catalog

## Tenant

-   Users
-   Agents
-   Calls
-   Conversations
-   Documents
-   Memory
-   Billing

# 8. Feature Flags

Per-tenant feature flags enable staged rollouts and subscription plans.

# 9. Usage Metering

Track per tenant:

-   Voice minutes
-   AI tokens
-   Storage
-   Embeddings
-   API requests

# 10. Security

-   JWT authentication
-   Row Level Security
-   Audit logging
-   Least privilege

# 11. Scalability

Supports:

-   Thousands of tenants
-   Millions of conversations
-   Partitioned tables
-   Read replicas
-   Dedicated enterprise databases (future)

# 12. Design Principles

-   Tenant-first
-   UUID everywhere
-   PostgreSQL is source of truth
-   Redis for performance
-   RLS enabled on tenant tables

# 13. Summary

This document defines the logical multi-tenant architecture that all
future schemas, APIs, and services must follow.
